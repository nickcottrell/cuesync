# Security Red-Team Report: Authentication and Tenant Isolation

Scope: static review of the inbound relay authentication boundary, replay behavior, webhook routing, tenant isolation, and fail-closed behavior in `relay.py`.

| id | file:line | finding | severity | recommended fix |
|---|---|---|---|---|
| CS-RT-01 | `relay.py:186-198` | The HMAC itself uses `hmac.compare_digest`, but the prerequisite SHA-256 key-hash check uses ordinary string inequality, creating a timing side channel on the configured key hash. | Medium | Decode and length-check both hashes, then compare fixed-length bytes with `hmac.compare_digest`. |
| CS-RT-02 | `relay.py:180-198`, `relay.py:309-388` | A valid signature has no signed timestamp, expiry, or nonce; the only replay control is the globally unique `cue_id` database key, so a captured request can be replayed until its ID is stored and remains reusable after database reset/rotation. | High | Require a signed timestamp plus nonce, enforce a short clock window, and persist consumed nonces for at least that window. |
| CS-RT-03 | `relay.py:313-327` | The long-term HMAC secret is sent in every request as `X-CueSync-Key`; any request capture yields the signing capability, rather than merely a reusable signature. | High | Store the HMAC secret at both ends and send only a key identifier and signature over a domain-separated canonical request. |
| CS-RT-04 | `relay.py:35-40`, `relay.py:367-388`, `relay.py:415-428` | There is one shared upstream credential, tool map, and store, with no authenticated tenant identity; any holder of the shared key can select every configured tool, so tenant A can route payloads to tenant B's webhook/drop. | Critical | Bind a tenant ID into the signed message and credential, then enforce tenant-scoped tool authorization and storage in every access path. |
| CS-RT-05 | `relay.py:309-327`, `relay.py:367-375` | Neither `X-Maestro-Hook` nor a tenant header is validated or used as an authorization gate; adding or forging either header has no effect, while possession of the shared key bypasses any intended per-hook/per-tenant boundary. | High | Reject requests unless a signed tenant and hook identifier resolve to an explicit tenant-owned allowlist entry. |
| CS-RT-06 | `relay.py:261-291` | `/health` and `/stats` are unauthenticated and disclose the relay ID, configured tool names, expiry/renewal state, and aggregate inbox/drop activity to any network caller. | Medium | Require an operator-scoped credential for detailed health/stats and expose only a minimal readiness result publicly. |
| CS-RT-07 | `relay.py:224-236` | Outbound webhook deliveries carry no HMAC/Ed25519 signature or tenant-bound authentication, so a receiver cannot distinguish CueSync from a forged raw POST or detect payload replay. | High | Sign each outbound body with a destination-specific key and include a verified timestamp, nonce, tenant, and delivery ID. |
| CS-RT-08 | `relay.py:310-311`, `relay.py:336-385` | Malformed framing and authenticated but wrong-shaped JSON are not comprehensively handled: invalid `Content-Length`, scalar JSON, or invalid field types can raise uncaught exceptions, failing the individual request closed but enabling handler-level denial of service and unreliable error behavior. | Medium | Strictly bound and parse content length, require a JSON object with typed/size-limited fields, and convert all validation failures to deterministic 4xx responses. |
| CS-RT-09 | `relay.py:423-430`, `relay.py:313-327` | The server binds to all interfaces and does not provide TLS; because the protocol transmits the long-term signing key, a deployment without a correctly configured external TLS terminator exposes both payloads and signing authority. | Critical | Require HTTPS with certificate validation end-to-end and refuse non-TLS public deployment. |

## Clean areas

- **Signature stripping / unsigned inbound routes:** `POST /cue` rejects missing signature or key headers before parsing or storing, and every other POST path returns 404 (`relay.py:297-334`, `relay.py:387-409`); no inbound raw-webhook acceptance route is present.
- **HMAC payload integrity:** the signature covers the exact request-body bytes and is checked with `hmac.compare_digest` (`relay.py:191-198`), so body modification without the secret fails closed.
- **Duplicate ID handling:** `cue_id` is a SQLite primary key and duplicate insertion returns a conflict (`relay.py:72-83`, `relay.py:91-113`, `relay.py:387-396`), providing durable duplicate suppression while the database is retained.
- **Destination injection:** callers select a configured tool rather than supplying an arbitrary URL, and unknown tools are rejected (`relay.py:57-59`, `relay.py:216-220`, `relay.py:367-375`); this is an effective SSRF boundary within a single trust domain, but not a tenant boundary.
- **Malformed/unsigned acceptance:** missing auth, invalid HMAC, invalid JSON, missing required fields, unknown tools, and duplicate IDs do not reach successful storage (`relay.py:317-396`); the robustness caveat in CS-RT-08 remains.
- **Ed25519:** no Ed25519 verification path exists, so there is no Ed25519 implementation to assess; the sole implemented signature scheme is HMAC-SHA256 (`relay.py:174-198`).
